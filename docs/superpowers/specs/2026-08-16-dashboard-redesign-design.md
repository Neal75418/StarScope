# 儀表板重設計

追蹤 94 個 repo 的儀表板，重心從「這批東西的現況」改成「什麼在動、什麼需要處理」。

本文的量測都在 2026-08-16 取得：星數與成長分佈來自正式資料庫（SQL 附在各節），
版面高度來自瀏覽器實測（指令附在該節）。數字會漂移，結論（分佈是雙峰、
絕對值指標不適用）不會。

## 為什麼

現況的問題不是資料錯，是版面沒有層級，而且成長指標量錯了東西。

量測（`document.querySelector('.dashboard-page')` 逐一取 `getBoundingClientRect().height`）：

| 區塊 | 高度 | 資料點 |
|---|---|---|
| 最近活動 | 840px（全頁 35%） | 10 |
| 近 7 天摘要 | 633px | 18 |
| 增長速度分佈 | 262px | 0 |
| 組合星數歷史 | 238px | 0 |
| 組合健康分數 | 166px | 0 |
| 統計卡 | 127px | 4 |

全頁 2425px，視窗 1267px。**佔版面最大的區塊資訊量最低**，而唯一密集有內容的
那一張從 y≈490 才開始，一半在摺線下。

每張卡的背景、邊框、圓角、內距、標題級數完全相同，所以「活躍警報」（需要行動）
與「星星總數」（純虛榮）視覺權重一樣。監控型頁面的任務是一眼看出要不要做事，
現況要讀完整頁才知道。

## 決定

三段式，依「漏看的代價」由高到低排列。使用者選擇保留全部四類資訊
（有事發生／在動／可讀／整體現況），所以這是排序問題不是取捨問題。

段序為：需要注意 → 在動 → 可讀。「在動」放主位，因為使用者指認
「錯過起飛的時機」是最不能接受的漏看。

## 成長指標改用相對值

這是本次唯一改變資料語意的決定。

追蹤清單的星數跨度從 1k 到 40 萬（`SELECT stars FROM repo_snapshots WHERE
snapshot_date=(SELECT MAX(snapshot_date) FROM repo_snapshots)`；2026-08-16 的分佈為
1k–10k 七個、10k–50k 三十九個、50k–150k 二十九個、150k+ 十九個）。

現行「增長速度分佈」用絕對值分桶（0-10、10-50、50-100、100+）。在這種跨度上，
一個 20 萬星的 repo 一天多 100 顆是死水，一個 5 千星的 repo 一天多 100 顆是爆發，
兩者落在同一格。實測當日：

| repo | 原星數 | 單日增加 | 相對 |
|---|---|---|---|
| deepseek-ai/deepseek-harness | 113,968 | +8,819 | +7.74% |
| cathrynlavery/diagram-design | 18,451 | +574 | +3.11% |
| mattpocock/skills | 218,276 | +431 | 0.20% |

按絕對值排，`diagram-design`（+574，真的在飛）與 `skills`（+431，雜訊）緊鄰；
按相對值排，兩者差 15 倍。

前端可直接計算，不需要後端改動：`delta / (stars - delta)`，兩個欄位都已在
`/api/repos` 的回應裡。下一節的中位數同樣在前端算——`/api/repos` 本來就回全部
追蹤中的 repo，算中位數需要的母體已經在手上，不需要新端點。

## 顯著與雜訊的界線

單日相對成長的分位數（查詢見下）：中位數 0.0093%、p90 0.0410%、p95 0.0600%、
最大值 8.2839%。**p95 與最大值差 138 倍，而 0.2% 到 3% 之間沒有任何 repo。**

```sql
WITH d AS (
  SELECT 1.0*(s2.stars-s1.stars)/NULLIF(s1.stars,0) AS rel
  FROM repo_snapshots s1 JOIN repo_snapshots s2
    ON s1.repo_id = s2.repo_id
   AND s1.snapshot_date = date('now','-1 day')
   AND s2.snapshot_date = date('now')
  WHERE s1.stars > 0)
SELECT rel FROM d ORDER BY rel;
```

分佈是雙峰的，所以門檻不敏感：中位數 ×10、中位數 ×20、絕對 >0.5%、絕對 >1%
在 2026-08-16 都選出同一批 2–3 個。

中位數的取樣母體是**所有算得出相對成長的 repo，含零與負值**——不是只取正成長的。
用正成長子集會讓門檻隨「今天有幾個在漲」而跳動，失去自我校準的意義。

採用**中位數 ×10**。理由不是它今天選得最準（幾個候選都一樣），而是
**同一條規則在任何時間窗都成立**：七日窗的中位數自然約為單日的七倍，門檻跟著長，
不必為每個窗重新調參。清單整體變熱時標準自動變嚴，冷下來時中等幅度的移動也會浮出。

面板**永遠顯示相對成長最高的 5 個（僅取正成長）**，在中位數 ×10 的位置畫一條
分隔線。線以上是真的在動，線以下是雜訊。永遠有內容，但不假裝線下那些值得看。
正成長不足 5 個時就顯示實際有幾個，不用負值補位——下滑是另一件事，另組呈現。

中位數為 0 時（整份清單完全不動）門檻退化為 0，此時不畫線——沒有東西可以稱為顯著。

## 時間窗

`stars_delta_7d` 與 `stars_delta_30d` 已存在，**沒有單日差值**。而七日差值需要七天前的
快照，快照起點是 2026-08-15，所以 2026-08-22 之前算不出來。

新增 `stars_delta_1d`。`analyzer.calculate_delta` 本身已是泛用的，但**直接沿用會出錯**。

### 回溯上限必須跟窗口成比例

`_find_snapshot` 找不到目標日期的快照時會往前搜尋，而上限寫死為七天，與請求的窗口無關：

```python
for offset in range(1, 8):    # 固定 7 天
```

七日窗回溯七天，誤差最多一倍。**單日窗回溯七天是七倍誤差**——昨天的快照缺一筆，
就會拿上週的來比，那個 repo 會帶著七天的成長量出現在「近 1 天」排行的第一名，
而且畫面上看不出任何異常。段二整個設計就是「相對成長最高的排最上面」，
這會直接製造出假的第一名。

改為 `min(days // 2, 7)`——與窗口成比例，但保留原有的絕對上限：

| 窗口 | 現行（固定 7） | 改後 | 實際窗口 |
|---|---|---|---|
| 1 天 | 7 | **0**（僅精確匹配） | 1 天 |
| 7 天 | 7 | **3** | 7–10 天 |
| 30 天 | 7 | 7（`min` 生效） | 30–31 天 |

三十日窗的實際範圍是 30–31 天而非 30–37：`calculate_signals` 只預載 31 天內的快照，
所以七天的回溯上限在該窗口下永遠碰不到，`min` 在這裡是防禦性的而非作用中的。

只寫 `days // 2` 會讓三十日窗的回溯上限變成十五天，實際窗口放寬到四十五天——
修好短窗卻弄壞長窗。加上 `min(…, 7)` 之後三個窗口都不劣於現況。

單日窗因此退化為精確匹配——昨天沒有快照，該 repo 當天就不進排行。那是誠實的結果，
比拿上週的數字冒充好。

這同時修掉一個既有缺陷：現行的 `stars_delta_7d` 可以回溯到十四天前仍稱作「七天」。
本次一併改動，屬於既有行為變更，測試要涵蓋。

### 用哪個窗

取**有資料的最寬窗**。「有資料」的判定是比較涵蓋範圍，不是「有沒有任何一筆」：
**七日窗算得出來的 repo 數 ≥ 單日窗時才切到七日**。否則 8/22 當天可能只有少數 repo
補齊了七日資料，排行榜卻已切過去，變成三列。標題明講是哪一個：

```
在動（近 1 天）      ← 快照不足七天時
在動（近 7 天）      ← 之後
```

標題帶窗口是刻意的。這個頁面已經有過一次「兩個同名而規則不同的數字」的教訓
（見「統一 weeklyStars」），不能再犯。

## 段一：需要注意

必須經常是空的。每天都亮的警示等於壁紙，所以入選標準要高。

**算數的**

| 來源 | 判定 |
|---|---|
| 未確認的觸發警報 | `triggered_alerts.acknowledged = 0` |
| 本週帶標記的新版本 | `context_signals` 中 `signal_type='release'`、`published_at` 在七天內、`tags` 含 `breaking` 或 `security` |

**刻意不算的**

- `deprecation` 單獨出現：那是預告不是行動。它仍以標記形式出現在段三。
- 停更（`pushed_at` 久未更新）：是狀態不是事件，會有二十幾個 repo 永久掛著。
- 抓取連續失敗：`scheduler._track_repo_failure` 只寫進記憶體的 dict，重啟即失，
  無法查詢；且那是應用自身的健康問題，不屬於追蹤清單。
- `archived`：資料是免費的（星號同步的回應裡就有），但 2026-08-16 的清單裡有 0 個，
  沒有真實案例可驗證整條鏈。列為後續獨立改動。

### 空狀態必須講出自己的覆蓋範圍

「本週無需注意的事」是一個安全承諾。而查詢顯示目前 `alert_rules` 有 0 筆，
所以警報那個來源永遠不會觸發——在沒有檢查過任何東西的情況下宣稱沒事，
與「velocity 是 null 卻算成停滯」是同一個錯誤，只是代價更高：段一是整頁唯一一個
「你可以不看」的承諾。

```
未設規則時 →  本週無需注意的事 · 未設定警報規則
有設規則時 →  本週無需注意的事
版本未抓取 →  正在檢查（版本資料尚未抓取）
```

括號那句同時是提示：警報系統存在但從未被使用。

## 段二：兩層，持久在上、即時在下

排行是即時的，它只回答「此刻誰在動」。而使用者要的是不要**錯過**起飛——
某個 repo 星期二暴衝，星期五才開 app 時，單日排行顯示的是星期五，星期二那件事
已經不在畫面上。**會遺忘的面板無法滿足「不錯過」。**

專案已經有會記住的機制：`anomaly_detector.detect_sudden_spike` 偵測到暴衝時寫入
`early_signals`，該列一直存在直到使用者確認。`SignalSpotlight` 元件已經負責呈現它們
並提供確認動作（`useDashboard` 的 `acknowledgeSignal`）。

所以段二是兩層，上層直接沿用 `SignalSpotlight`：

| 層 | 內容 | 生命週期 |
|---|---|---|
| 上 | 未確認的早期訊號（暴衝／竄升／突破） | 持久，使用者按「知道了」才消失 |
| 下 | 相對成長排行前 5 名 + 中位數 ×10 分隔線 | 即時，每次載入重算 |

上層平時是空的（`SignalSpotlight` 在無訊號時回 `null`），那時段二就只有排行。

`signalSpotlight` 在自訂器裡**保留為可關閉**，維持現狀。但關掉它等於放棄段二的
持久層——排行仍在，只是不再記得幾天前發生過什麼。這個取捨屬於使用者，
不由實作決定；自訂器的說明文字應該讓它看得出來，不要只寫一個元件名稱。

時程上這也比較好：異常偵測只需要三筆快照（`anomaly_detector` 有
`len(snapshots) < 3` 的守衛），快照起點 2026-08-15，所以 2026-08-17 就開始運作，
比七日 velocity 的 2026-08-22 早五天。

## 訊號總覽解散

現行「近 7 天摘要」裡的「訊號總覽」有四個數字，改版後各自有更好的去處：

| 數字 | 去哪 |
|---|---|
| 觸發警報 | 段一的項目 |
| 早期訊號 | 段二上層的項目**本身**，不再只是一個計數 |
| 加速中 / 減速中 | 被段二的排行取代（排行看得到是誰，計數看不到） |

把計數換成東西是升級不是搬家：「早期訊號 2」不能點、不能確認、不告訴你是哪兩個。

## 四張統計卡的去向

整排移除，但四個數字各有歸屬——沒有一個是憑空刪掉的：

| 現在的卡 | 去哪 |
|---|---|
| 追蹤數量 94 | 段一的狀態列：`本週無需注意的事 · 94 個追蹤中 · 3 分鐘前更新` |
| 活躍警報 | 段一的項目（有值時才出現） |
| 近 7 天星數 | 段二的標題列：`在動（近 7 天）· 全體 +9,892` |
| 星星總數 8.3M | `WidgetCustomizer` 預設關閉 |

「近 7 天星數」移到段二標題是刻意的：它是「整體動能」，跟段二那份排行講的是同一件事，
放在一起才互相解釋——排行看個體、標題看總和。放在頁面最上面當一張獨立的卡時，
它跟旁邊的「追蹤數量」看起來是同一類東西，實際上完全不是。

這也讓下一節的統一有意義：如果「近 7 天星數」被整個拿掉，統一兩套算法就只是
清理無人使用的程式碼；它留在段二標題，那個數字就會被讀，規則不一致就會被看見。

## 段三：可讀

沿用現有的「本週新版本」與「HN 提及」，並排，往下滾。不改邏輯。

## 移除採用「預設關閉」而非刪除

星星總數、組合星數歷史、最近活動、增長速度分佈改為 `WidgetCustomizer` 的
`DEFAULT_VISIBILITY` 中預設 `false`，程式碼保留。組合健康分數同樣改為預設關閉——
原本規劃把它縮成段一的一行，但段一的設計原則是「必須經常是空的」，
加一個永遠都在的分數與該原則直接衝突。它的資訊已由段一的狀態列與段二的排行承擔。

理由：這四項在 2026-08-16 合計佔 1506px、提供 4 個資料點，但「哪些面板值得留」
是使用者的判斷不是實作者的。切換開關已經存在，預設值是最小且可逆的表達方式。

### 只改預設值不夠

`loadWidgetVisibility` 的合併方式是 `{...DEFAULT_VISIBILITY, ...parsed}`，已存的鍵
會蓋過新的預設值。使用者只要曾經打開過那個選單並切過任何一個開關，八個鍵就全部
寫進 localStorage，之後改 `DEFAULT_VISIBILITY` **完全沒有作用**。

2026-08-16 實測該使用者的 `starscope-dashboard-widgets` 為 `null`（沒存過），
所以現在改會生效——但這個前提在動手之前隨時可能失效。

作法是**更換 storage key**（例如加上版本後綴）。既然這次改版本身就改變了版面的
widget 組成，舊的偏好對不上新的版面，重置是正確的結果而不是損失。加遷移邏輯去
猜「哪些鍵是使用者刻意設的」不值得。

## 統一 weeklyStars

同一頁上目前有兩套規則計算同名的數字：

- KPI 卡（`useDashboard`）：每個 repo 的 `stars_delta_7d` 加總。該值來自
  `analyzer.calculate_delta`，找不到七天前的快照時**往前再找最多七天**。
- 摘要徽章（`weekly_summary`）：最新快照減去「`snapshot_date <= period_start` 之中
  最新的那一筆」，**沒有回溯上限**。

兩者的回溯窗不同，資料累積後會開始各說各話。統一為前者的規則（有上限的回溯），
因為無上限回溯可能拿三個月前的快照冒充「七天前」。

## 測試

- 相對成長的計算與排序：含 base 為 0、delta 為 null、以及大小 repo 混合的情況
- 中位數 ×10 的門檻：整份清單不動時不畫線；只有一個 repo 時不炸
- 時間窗選擇：七日有資料時用七日，沒有時退回單日，標題跟著變
- 段一的空狀態三態：未設規則／已設規則／版本未抓取，各自的文案不同
- 段一的入選：`deprecation` 單獨出現不入選，`breaking` 入選
- 回溯上限：單日窗缺前一天快照時回 `None` 而非拿更早的；七日窗最多回溯三天；
  三十日窗維持七天（`min` 的上限有生效，沒有被 `days // 2` 放寬）
- 時間窗切換：七日涵蓋數 < 單日時不切換
- 段二兩層：有未確認訊號時上層出現、確認後消失、無訊號時只剩排行
- widget 預設值：舊 storage key 的內容不影響新版面
- 版面：三段之間有間距、無區塊貼合（延續 `.dashboard-page` 的 flex gap）

延續本專案的既有作法：每一條行為變更都以突變測試驗證——把實作改回舊行為，
確認對應的測試轉紅，還原後檔案位元組相同。

## 風險

**單日窗比七日窗嘈雜。** 單日的相對成長會被單一新聞事件主導。緩解方式是標題明講
窗口，且七日資料一出現就自動切換。2026-08-22 之後應重新檢視分隔線的位置是否仍合適。

**中位數 ×10 在清單極小時不穩。** 追蹤數量少於 10 個時中位數本身沒有意義。
此時仍顯示前 5 名，但不畫線。

**「需要注意」可能長期為空。** 這是設計意圖而非缺陷；若連續數週為空且使用者從未
設定警報規則，該考慮的是提示設定規則，而不是降低入選標準。
